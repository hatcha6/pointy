# Pointy POS — Beta Performance Audit

## 1. Executive Summary

Pointy is in solid shape for beta, but a handful of issues will bite hard once shops cross the "real data" threshold (tens of thousands of products, months of sales/PO/notification history). The dominant pattern is **heavy serializers and Python-side aggregation running unbounded on growing time-series tables** — most acutely the notifications endpoint recomputing whole-catalog scans on every badge poll, the analytics export materializing the entire event table in RAM, and the inventory/catalog serializers firing N+1 product-tree cascades. On the client, the **POS hot path rebuilds too broadly** and **two contact pickers fire a network request per keystroke** (including during checkout). On the relay, the **AI HTTP client never pools connections to OpenRouter** and **a single slow stream can head-of-line-block every device on a shop's tunnel session**. None are blockers, but the items in the quick-wins table below are cheap and should land before beta.

## 3. Backend (Django)

### Critical
*(none)*

### High

**Full notifications recompute runs synchronously on every notifications GET** — `backend/apps/notifications/views.py:34-37`
`get_queryset()` calls `sync_business_notifications()` for `list`/`retrieve`/`refresh`, inline in the request thread. That function runs 8 full recompute passes (inventory, expiry, purchasing, printing, sales, fraud, discount, payroll) and upserts every spec inside one transaction — including loops over every active `StockItem`, every non-cancelled all-time `PurchaseOrder`, and every closed all-time `RegisterSession`. A Celery beat already runs the same task every 15 min (`settings.py:253-257`), and the module docstring (`services.py:576-578`) explicitly says it runs on both. **At scale:** the bell/badge is polled by every signed-in device; at tens of thousands of products plus months of history, each poll loads tens of thousands of rows into Python and re-walks all-time PO/session tables, multiplied by concurrent devices, exactly when the shop is busiest. **Fix:** remove the sync call from `get_queryset`; serve `visible_notifications_for_user()` directly from the beat-maintained table. Keep `POST /refresh` for manual recompute, and trigger the Celery task (debounced) on relevant domain events if tighter freshness is needed.

**Inventory and overdue-PO notification specs iterate every row in Python instead of filtering in SQL** — `backend/apps/notifications/services.py:206-237` (and `:298-353`, `:407-436`)
`_inventory_notifications` loads ALL active `StockItem`s and decides out-of-stock/low-stock in Python (`item.quantity_on_hand <= item.reorder_level` is an F()-expressible DB filter); `_purchasing_notifications` and `_sales_notifications` similarly pull every non-cancelled PO and every closed register session over all time. Only a tiny fraction of rows ever produce a notification. **At scale:** ~30k `StockItem` rows materialized per sync on a 30k catalog, plus unbounded PO/session loops; combined with the per-GET invocation above this is the dominant cost. **Fix:** push predicates into SQL — `StockItem.objects.filter(Q(quantity_on_hand__lte=0) | Q(quantity_on_hand__lte=F('reorder_level')))`; filter overdue POs (`due_date < today` and balance > 0) at the DB level using the already-annotated paid/credit totals; bound register-variance scanning to recently-closed sessions. Shrinks each scan from O(catalog)/O(history) to O(actual-alerts).

**Analytics events export builds the entire (unbounded, unfiltered) event table in memory** — `backend/apps/analytics/services.py:125-180`
`build_events_export_zip` opens a `zipfile.ZipFile` over an in-memory `BytesIO` and writes every row into an in-memory `StringIO` via `queryset.iterator()`, then returns the full zip bytes through a buffered `HttpResponse`. The query serializer (`serializers.py:131-198`) makes every filter optional with no default date window and no row cap, so an unfiltered GET exports the whole `AnalyticsEvent` table — the highest-volume table in the system. **At scale:** millions of rows materialize the full result set as a Python string + zip bytes (hundreds of MB to GB), blocking a worker and risking OOM on one manager click. **Fix (both, with in-repo precedent):** (1) enforce a hard row ceiling / bounded date window in `validate()` — reject windows wider than ~90 days or cap rows like the expense ledger's `LEDGER_ROW_LIMIT`; (2) replace the in-memory build + buffered response with a `StreamingHttpResponse` (already used in `apps/ai/views.py`) yielding CSV rows from `queryset.iterator()` so memory stays flat. Push very large exports to a background `ReportRun`-style job.

**ProductCatalogSerializer.modifier_group_details fires a fresh query per product (bypasses prefetch)** — `backend/apps/catalog/serializers.py:268-277`
`product_modifier_group_details` builds a *fresh* queryset off `product.modifier_group_links` with `select_related/prefetch_related/order_by`, so it ignores any prefetch cache and hits the DB once per product (plus `group__options`). `ProductViewSet.queryset` prefetches neither `modifier_groups` nor `modifier_group_links`. **At scale:** this runs on the POS catalog (`?is_active=true`) and the products list — both `PAGE_SIZE=50` — so a thousands-product shop pays 50-100 extra queries per page on the screen cashiers hit constantly; it also amplifies the two inventory N+1 findings below. **Fix:** add `Prefetch('modifier_group_links', queryset=ProductModifierGroup.objects.select_related('group').prefetch_related('group__options').order_by('display_order','id'))` to the viewset (in `get_queryset`, so retrieve/product_detail benefit too), then rewrite `product_modifier_group_details` to consume the cache: `links = product.modifier_group_links.all()` with no further chaining.

**StockMovement list embeds full ProductCatalogSerializer with no prefetch (N+1 cascade)** — `backend/apps/inventory/serializers.py:79-99`
Each `StockMovement` row serializes the full heavy `ProductCatalogSerializer` for `variant.product`, but the viewset (`views.py:89`) only `select_related`s variant/product/stock_item/created_by and prefetches nothing the catalog serializer traverses — so each row re-fires ~10+ queries for the product tree. **Notable:** the frontend `StockMovement.fromJson` (`stock_movement.dart:52-68`) never reads `product_detail` — or even `variant_sku/variant_name`; the entire tree is dead payload. **At scale:** the movement ledger is append-only; a 50-row page does ~500+ queries on a months-old history. **Fix (strictly better):** remove `product_detail` from `StockMovementSerializer` entirely (and optionally the unused flat variant fields), keeping the already-used flat `product` id. If it must be retained, include it only on `retrieve`; if it must stay on list, mirror the catalog `ProductViewSet` prefetch with the `variant__product__` prefix.

### Medium

**StockItem list embeds full ProductCatalogSerializer with no prefetch (N+1 cascade)** — `backend/apps/inventory/serializers.py:8-9`
The inventory stock-on-hand list renders the full `ProductCatalogSerializer` per row via `product_detail`, but `StockItemViewSet.queryset` only `select_related`s variant/product. None of the deep relations are prefetched, and `quantity_on_hand` falls back to a per-product aggregate (`catalog/models.py:200-207`). **At scale:** a shop with tens of thousands of variants does ~50 full product expansions per 50-row page. **Fix:** prefetch the `variant__product__` chain the catalog serializer reads and annotate stock to kill the aggregate N+1 — or (preferable for a stock list) replace `product_detail` with a lightweight summary serializer and keep the full one only on retrieve. Back-office screen, not hot-path, so medium.

**Product list sorts by unindexed `name` on every POS/catalog load** — `backend/apps/catalog/models.py:176-177`
`Product` has `ordering = ["name"]` (re-applied as `order_by("name","id")` in `views.py:213`) but `name` has no index. Every product-list page and POS catalog fetch sorts the filtered set with no supporting index. **At scale:** the POS catalog is the single most frequently hit list; tens of thousands of products get sorted on every open/scroll. **Fix:** add a partial index `models.Index(fields=["name","id"], name="product_name_live_idx", condition=Q(archived_at__isnull=True))` (the live catalog always filters `archived_at IS NULL`). Verify with EXPLAIN on a populated dataset — on the cached `id__in` POS path the planner may still sort.

**PurchaseOrder lacks `(status, -created_at)` composite index** — `backend/apps/purchasing/models.py:125-139`
PO is `ordered by -created_at` (no index on `created_at`) and routinely filtered by status across the PO list, payables, and dashboard date-range aggregates. `Order` already has this exact index (`sales/models.py:295-303`); PO lacks the mirror. **At scale:** months of POs scan/sort without an index. **Fix:** add `models.Index(fields=["status", "-created_at"], name="po_status_created_idx")` to `PurchaseOrder.Meta`. Skip a standalone `-created_at` index — the composite's leading column already serves the ordered list.

**Job board filters status with no `(status, -created_at)` index** — `backend/apps/operations/models.py:208-209`
The jobs board lists jobs filtered by status (and job_type) ordered by `-created_at`, but `Job` has no DB indexes — only `Meta.ordering`. **At scale:** an operations shop with months of completed jobs scans the table for the (usually open) board. **Fix:** add `models.Index(fields=["status", "-created_at"], name="job_status_created_idx")`. Low-volume, off hot path → low/medium.

**Fraud sweep loads 30 days of orders/adjustments/movements into Python loops on every risky action** — `backend/apps/fraud/metrics.py:112-349`
`build_cashier_metrics()` materializes every committed order (plus a payments prefetch), every adjustment, cash movement, closed session and reprint event over a 30-day window and sums per-cashier in Python — all pure SUM/COUNT-by-cashier that GROUP BY would do in the DB. It runs on a beat *and* via `schedule_targeted_sweep()` after every void/return/cash pay-out/register close (`sales/views.py:331/357/388/709/777`). **Mitigation:** the heavy work runs on a Celery worker via `on_commit`, so checkout is *not* blocked (the "multi-second job on every checkout" framing is overstated). **Unmitigated:** tens of thousands of orders + payment rows still materialized per sweep, and there is no debounce, so bursts of risky actions pile up on the broker. **Fix:** replace per-row loops with `.values('register_session__owner_id').annotate(...)` aggregates (use `distinct=True` on the payments-joined cash count); keep only the bounded (≤12) evidence lists as a small separate query; debounce/coalesce `schedule_targeted_sweep`.

**Register Z-Report sums an entire session's orders and lines in Python** — `backend/apps/sales/register_summary.py:106-173`
`_sales_and_categories` loads every committed order for a session plus a deep line/variant/product/category prefetch, then sums gross/discount/total/items in Python. **At scale:** a long busy shift accumulates thousands of orders pulled into memory just to produce a handful of totals, when a manager opens the summary or prints the Z-Report. **Fix:** (1) order-level scalars via one `orders.aggregate(Sum('subtotal'), Sum('discount_total'), Sum('total'), Count('id'))` — these are real DB columns. (2) For lines/categories/items, do **not** load full `Order` objects; `OrderLine.line_total` is a Python property, so iterate a lean `OrderLine.objects.filter(order__in=orders)` annotated with `line_net = F('unit_price')*F('quantity') - F('discount_total')`, selecting `.values('quantity','line_net','variant__product')`. `items_sold` and the primary-category grouping must stay at the line level (correction to the original fix).

**Discount rule performance/beneficiaries load all redemptions into Python to sum** — `backend/apps/discounts/analytics.py:29-178`
Both endpoints do `list(DiscountRedemption.objects.filter(rule=rule)...)` — every redemption ever recorded for the rule, with three `select_related` joins — then sum/count/group/trend in Python. An always-on automatic rule records one redemption per triggering sale. **At scale:** tens of thousands of rows loaded into memory each time a manager opens the performance tab. **Fix:** push the scalar summary to `aggregate(discount_amount=Sum(...), influenced_gross=Sum('applied_discount__source_subtotal'), redemption_count=Count('id'))`; channel/monthly via `.values('channel')`/`TruncMonth(...).annotate(...)`. **Caveat:** `document_count` is a distinct count over a *composite* key (`document_content_type_id` + `document_object_id`) — use `Count(Concat(...), distinct=True)`, not a naive single-field distinct. For beneficiaries, group in SQL and batch-resolve customer/supplier names.

**`outstanding-received-not-paid` loads ALL received POs (13-table prefetch) into memory, filters & paginates in Python** — `backend/apps/purchasing/views.py:403-419`
The action filters to RECEIVED then fully evaluates the queryset into a Python list to compute `balance_due` (a property) and filter/sort *before* `paginate_queryset`. The base queryset carries ~13 prefetch chains, and `get_queryset` only swaps to a lighter set when `action == "list"` — so this action runs the full prefetch + full `PurchaseOrderSerializer`. Pagination only trims output. The payables screen calls it on open. **Fix:** push the unpaid filter into SQL — annotate `paid`/`credit` via conditional `Sum`, `.filter(F("total") - paid - credit > 0)`, order in SQL with `nulls_last`, then `paginate_queryset(queryset)`. Drop the heavy prefetch for this action. (`balance_due` only needs total/paid/credit, not `supplier_credits`/adjustments.)

**Dashboard purchasing section materializes every non-cancelled PO to compute balances in Python** — `backend/apps/core/dashboard/helpers.py:478-531`
`_purchase_order_balance_rows` wraps the annotated queryset in `list(...)` over all non-cancelled POs, looped twice per cache miss (due_total + top-supplier). **Mitigation:** per-section cache (`DASHBOARD_SECTION_CACHE_SECONDS=30`, global scope) limits it to ~once/30s shop-wide. **At scale:** a tens-of-thousands-element list built and looped twice on the first dashboard hit after each 30s window. **Fix:** compute `due_total` and overdue count via SQL aggregates; for `_top_supplier_balances`, push the per-PO balance sum to `.values("supplier_id").annotate(Sum(Greatest(...)))` — but note it also nets per-supplier unallocated payments + open credits in Python (not a pure top-N), so the final netting/sort stays in Python over a bounded per-supplier set.

**`customer_insights` at_risk / outstanding_credit and `project_forecast` aggregate all-time in Python** — `backend/apps/ai/tools.py:1207-1216`, `:1256-1278`, `:1399`
`at_risk` aggregates over ALL committed sales for all time, pulls one row per customer to Python, then filters/sorts/slices — unlike `top` mode which does `.order_by('-spend')[:limit]` in SQL. `outstanding_credit`/`project_forecast` materialize every open-credit order plus all payments to compute `balance_due` per order with no DB limit. `business_health` calls both. **Fix:** for at_risk, push the cutoff into a HAVING + order/limit: `.annotate(last_order=Max('created_at')).filter(last_order__date__lt=cutoff).order_by('last_order')[:limit]`. For receivables, annotate `paid=Coalesce(Sum('payments__amount'),0)`, `balance=Greatest(F('total')-F('paid'),0)`, `.filter(balance__gt=0)`, then aggregate total and group top-N debtors by customer in SQL. Share one helper so the two tools can't diverge.

**`inventory_intelligence` dead_stock/fast_movers scan is unfiltered and blindly capped at the first 500 stock rows** — `backend/apps/ai/tools.py:860-903`
For dead_stock/fast_movers there is no DB-side filter — the code scans `stock_qs[:500]` in default order and applies the predicate in Python. **This is a correctness-at-scale bug:** on a >500-variant catalog (routine at target scale) the tool inspects an arbitrary first 500 rows, so the largest tied-up dead stock and the true fast movers are silently invisible. `business_health` calls dead_stock and reorder every run. (reorder mode *is* DB-filtered, so it only bites when >500 items are simultaneously at/below reorder.) **Fix:** annotate `StockItem` with units-sold over the window via a correlated `Subquery` on `OrderLine` (reproducing the committed-sales scoping), filter `dead_stock` as `quantity_on_hand__gt=0, units_sold=0` and `fast_movers` as `units_sold__gt=0`, order by the ranking metric in SQL, slice to `limit`.

**`match_invoice_products` fans out the heavy product-list viewset up to ~600x per call** — `backend/apps/ai/tools.py:2159-2160`
For every invoice line, `_match_invoice_line` runs a full `ProductViewSet` `list` execution per search query (up to 6/line × up to 100 lines = ~600). Each runs permission checks, `_with_variant_rollups`, multi-join `icontains` search, a pagination COUNT, and serialization of up to 25 products with 9 prefetched relations — all discarded; the matcher reads only id/name/default-variant fields. **Mitigation:** `BoundedAiPagination` caps page_size to 25, and barcode-exact / learned-alias lines short-circuit. **Unmitigated:** barcode-less lines still pay the 6× fan-out with wasted prefetch + per-query COUNT. **At scale:** a 30-100 line wholesaler invoice → multi-second-to-tens-of-seconds latency, blocking the agentic turn. **Fix:** build the scoped queryset once via `_scoped_queryset(...)` (preserves permissions/row-scoping), strip prefetches with `.prefetch_related(None)`, drop COUNT/pagination, select only needed columns, and batch all lines' terms into one OR'd (or trigram) query matched in Python. Async AI flow, not transactional hot path → high not critical.

**`match_invoice_products` does a per-matched-line cost lookup (N+1 `latest_variant_unit_cost`)** — `backend/apps/ai/tools.py:2262-2266`
Each matched line calls `latest_variant_unit_cost(variant_id)`, one `PurchaseLine` query per line (up to 100). Dwarfed by the search fan-out above, but a real N+1. **Fix:** hoist out of the loop — add a bulk `latest_variant_unit_costs(variant_ids)` helper (one query, newest-first, keep first per variant, mirroring `supplier_candidates_for_variants`) and build a `{variant_id: cost}` map.

**Employee list: `active_compensation_plan` bypasses prefetch + `payroll_total` aggregates per row** — `backend/apps/employees/models.py:87-105`
`get_active_compensation_plan` calls a property that re-filters `self.compensation_plans` (a fresh queryset), ignoring the viewset's `Prefetch`; `payroll_total` is declared as an annotation-expecting `DecimalField` but never annotated, so DRF reads the aggregate property. Two extra queries per employee. **Mitigation:** employees are low-volume and `PAGE_SIZE=50` bounds it; HR/admin screen, not hot-path → low. **Fix:** filter the prefetched `compensation_plans.all()` list in Python; annotate `payroll_total` with `Coalesce(Sum('payroll_lines__net_amount', filter=~Q(...VOID)), Decimal('0.00'))`.

### Migration tooling (offline, one-time — lower priority)

**Product import does 4-8 DB round-trips per product, none batched** — `backend/apps/migration/loaders/catalog.py:100-154`
Per first-time product: `Product.save()`, `categories.set()` (SELECT + clear + insert), an identity-map INSERT, `ensure_default_variant()` (two SELECTs + create), and a second identity INSERT — ~7-8 statements/product, each in its own savepoint. No bulk path. **At scale:** 30-50k products → 150k-250k statements (tens of minutes to hours on a remote legacy source). Reads are already preloaded (`identity.py:40`), so `existing()` is in-memory on first import. **Cheap safe wins:** skip `categories.set()` when `category_ids` is empty; skip both variant SELECTs when the product was just created. Full bulk_create is L-effort and conflicts with the engine's per-record continue-on-error + idempotent-rerun savepoint model — pursue only in bounded chunks with per-row IntegrityError fallback.

**Connectors buffer entire child/line tables into memory dicts, defeating the streaming transport** — `backend/apps/migration/connectors/aboghris_mssql.py:390-403` (+ `fahd_mssql.py:364-392`)
`_lines_by_parent` materializes the entire `SALE_ITEMS`/`BUY_ITEMS` table into a `dict[str, list[dict]]` held in `ctx.cache` for the whole run; called eagerly at the top of `_sales`/`_purchase_orders`, defeating the transport's `fetchmany` streaming. `SALE_ITEMS` is the biggest table in a POS DB. **At scale:** hundreds of MB to low GB resident; can OOM-kill the import on a busy shop with years of history. **Fix:** stream grouped by parent — issue `SELECT ... ORDER BY parent_id` (via the streaming `iter_records`, *not* `raw_query`, which `fetchall`s) and emit each parent as the key changes, keeping one invoice's lines in memory. Fall back to parent-id range chunking if ordering is unreliable on legacy SQL Server. Apply the same to Fahd. Evict `ctx.cache` entries when an entity finishes.

**Stock reconstruction writes StockItem one `update_or_create` per variant in a per-variant savepoint** — `backend/apps/migration/reconstruct.py:292-312`
`flush()` loops every variant with movement and does `update_or_create` (SELECT + INSERT/UPDATE) inside its own `transaction.atomic()`. Reconstruct is the recommended path for drifted balances. **At scale:** 30-50k variants → ~100k-150k statements + 50k savepoints at the run tail. **Fix:** partition against existing StockItems with one `values_list`, `bulk_update` existing + `bulk_create` missing in batches, one transaction per batch — **but** wrap each batch in try/except and fall back to per-row `update_or_create` on IntegrityError to preserve the existing per-row `stock_write_failed` continue-on-error behavior.

**Lower-severity migration N+1s (offline):** identity map written one INSERT per entity (`identity.py:73-90`) — the per-row INSERT is *intentionally* coupled to the entity's savepoint for idempotent re-runs; do **not** naively batch it (the finding's proposed fix breaks the documented no-duplicate-on-rerun invariant). Generated default-variant SKU probes the DB with `.exists()` in a loop (`catalog/models.py:246-253`) — the two real connectors always emit a deterministic SKU, so prefer fixing connectors over relying on DB-constraint+nested-savepoint retry. Sale/PO re-run deletes child lines per parent (`loaders/sales.py:75-84`) — the loader can't bulk-delete across parents without an engine-level refactor; low priority.

## 4. Frontend (Flutter)

### Critical
*(none)*

### High

**Customer/supplier picker sheet reloads contacts on every keystroke (no debounce)** — `frontend/lib/src/shared/contact_picker_sheet.dart:484-491`
`_PickerShell` uses a raw `TextField` whose `onChanged` → `_load(reset:true)`, issuing a fresh server-paginated contacts request per keystroke. Backs customer-attach in POS and supplier-attach in purchasing. **At scale:** during an active sale, searching a customer fires one paginated query per keypress against a tens-of-thousands-row table — backend load + flicker at the most latency-sensitive moment. **Fix:** swap for the shared `DebouncedSearchField` (`shared/query_controls/debounced_search_field.dart`, 350ms + revision guard). One-widget change benefiting both pickers; pass the current `query.search` as `value`.

### Medium

**Contacts search fires 2 network requests per keystroke (no debounce)** — `frontend/lib/src/features/contacts/views/contact_management_screen.dart:473-479`
Raw `TextField` → `updateSearch` → `loadContacts()`, which resets pagination and issues two *sequential* awaited requests (`loadCustomers` then `loadSuppliers`). No in-flight cancellation, so later keystrokes can be overwritten by earlier responses. The most-used lookup screen; the rest of the app uses `DebouncedSearchField`. **Fix:** use `DebouncedSearchField` (16 requests → ~2 for an 8-char search); add a request-revision token to `loadContacts` to drop stale responses; optionally scope the load to the active tab.

**Operations jobs board page-drains ALL jobs into memory; unbounded for completed/all filters** *(merged: `operations_repository.dart` + `jobs_board_view_model.dart`)* — `frontend/lib/src/data/repositories/operations_repository.dart:39-71`
`loadAllJobs` loops every page (`while (hasMore)`) into one list; it's the only fetch path the view model uses (`loadAll`/`loadJobs` both call it). The board defaults to `open` (bounded), but the status filter accepts `completed` and `null` (all) (`jobs_screen.dart:503-519`), which removes the bound — the completed set grows forever. **Correction to render-side claims:** the flat (non-board) list already uses `ListView.builder` (`jobs_screen.dart:199`); the eager kanban paths (`_stageGroups` `:281-309`, `_KanbanBoard` `:820-863`) only render for `statusFilter == open`. The genuine defect is the data-layer drain, not widget virtualization. **Fix:** for non-open/historical views use the already-exposed paginated `loadJobs(page:)` + `hasMore` with incremental load-more (mirror `invoice_list_view_model.dart`); keep the page-drain only for the bounded open-jobs kanban.

**POS workspace rebuilds catalog grid + app bar + drawer on every cart tap** *(merged: pos_screen finding #1, #2, and pos_catalog_pane)* — `frontend/lib/src/features/pos/views/pos_screen.dart:46-97` (with `pos_catalog_pane.dart:68-89`)
A single root `ListenableBuilder` on `PosViewModel` wraps the whole body. Every cart mutation calls `_notifyChanged()` → `notifyListeners()`, rebuilding `PosCatalogPane.build` (re-running `_cartQuantitiesByProduct` into a fresh map, rebuilding `InfiniteScrollGrid` and all visible `ProductTile`s) plus the chrome — even though only the cart changed. `refreshDiscountPreview()` fires 1-2 more notifies per tap (2-3 full rebuilds/tap). **Corrections to original framing:** the grid *is* virtualized (only ~12-30 visible tiles rebuild, not the whole catalog); `QuickAccessCategoryStrip` does *not* re-fetch on rebuild (fetches once in `initState`); the closed drawer's subtree isn't built. So the cost is bounded but real on the hottest path. **Fix:** move app bar + drawer outside the root `ListenableBuilder` (wrap only the register-session pill); give the catalog and cart panes separate narrowly-scoped listeners (Selector/ValueListenable) so the catalog rebuilds only on products/query/loading and the cart pane only on cart/discount; drive per-card quantity badges off a dedicated `ValueListenable<Map<int,double>>`; add per-card `RepaintBoundary`. Note: merely preserving map identity is insufficient — `InfiniteScrollView` builds a new `SliverChildBuilderDelegate` each build (default `shouldRebuild==true`), so the fix must prevent `PosCatalogPane.build` from running on cart-line mutations.

**AI file attachment base64-encoded on the UI thread (images are offloaded, files are not)** — `frontend/lib/src/features/ai/ai_attachment_picker.dart:54-71`
Non-image attachments are `base64Encode(bytes)` synchronously on the main isolate with no size cap (`withData: true`, so full bytes are in memory). The adjacent image branch correctly offloads via `compute(...)` and downscales — a clear oversight. **At scale:** a 15-25 MB invoice PDF on a mid/low-end Android device blocks the UI thread several hundred ms right as the user taps send — the documented PO-from-invoice flow. **Fix:** mirror the image path — `dataUri = 'data:$mime;base64,' + await compute(base64Encode, bytes)`; enforce a max attachment size before encoding.

**Catalog/product images use `Image.network` with no on-disk cache** *(merged: `pointy_product_image_frame.dart:64` + `product_image_thumbnail.dart:35-53`)*
Both product-image widgets use bare `Image.network` with `cacheWidth/cacheHeight` (good for in-memory decode size) but only the in-memory `ImageCache` (~1000 images / 100MB, evicted on scroll). `cached_network_image`/`flutter_cache_manager` are not in `pubspec.yaml`. **At scale:** a large virtualized catalog re-downloads evicted thumbnails on every back-scroll, screen switch, and app restart — repeated bandwidth/latency and reload spinners, especially over a remote relay tunnel. Degrades gracefully (letter fallback), never blocks checkout. **Fix:** add `cached_network_image` and replace both `Image.network` calls with `CachedNetworkImage`, mapping `cacheEdge`→`memCacheWidth/Height`, with placeholder/errorWidget for the existing fallbacks. If the backend reuses URLs on image replacement, add a version/`updated_at` cache key.

### Low

**`PointyProductCard` wraps every card in a per-card `LayoutBuilder` + always-on `Opacity`** — `frontend/lib/src/shared/catalog/pointy_product_card.dart:57-73`
The per-card `LayoutBuilder` (just to derive `isCompact` from width) is redundant — the grid-level `LayoutBuilder` already computes per-tile width via `PointyProductCardGrid.tileWidthFor`. `Opacity(opacity: enabled?1:0.58)` adds a no-op render node when enabled. **Correction:** `RenderOpacity` short-circuits at alpha 255 — no `saveLayer`; it's an extra node + relayout closure, not compositing overhead. Bounded to visible tiles. **Fix:** pass resolved width/`isCompact` from the grid into the card; wrap in `Opacity` only when disabled.

**Operations board builds every job card eagerly for the open-jobs board** — `frontend/lib/src/features/operations/views/jobs_screen.dart:241-309`
Both board paths materialize a `_JobCard` per open job (stacked board via `ListView`+`Column`; `_KanbanBoard` via `SingleChildScrollView`+`Row`), and `jobsByStage` is recomputed in `build` on every notify. Only bites at hundreds of simultaneously-open jobs (unusual). **Fix:** lazy-build the stacked board (flatten to a `SliverList`/`ListView.builder`); for the horizontal kanban, make each column's inner card stack a vertical `ListView.builder`; memoize `jobsByStage` by `(template.id, jobs identity)`.

## 5. Relay (Go)

### Critical
*(none)*

### High

**AI HTTP client uses default Transport (MaxIdleConnsPerHost=2) for all OpenRouter fan-out** — `relay/internal/relay/ai.go:496-501`
`AIHTTPClient` is never assigned in `main.go`, so `aiHTTPClient()` returns a client with a nil Transport → `http.DefaultTransport` (MaxIdleConnsPerHost=2). All AI calls (stream + router + title + web-search classifier) target one host (`openrouter.ai`), so once >2 calls overlap nearly every call pays a fresh TCP+TLS handshake. **At scale:** a single turn issues 2-4 calls; dozens of concurrent turns across the fleet constantly tear down/rebuild TLS to one host (~100-300ms each + CPU). **Fix:** construct one shared `*http.Client` in `main.go` with a tuned Transport (`MaxIdleConns=200`, `MaxIdleConnsPerHost=100`, `IdleConnTimeout=90s`, `ForceAttemptHTTP2=true`) and assign to `baseHTTPHandler.AIHTTPClient` before the handler copies (pointer shared by value-copy — correct). Do the same for `ImageSearchHTTPClient`/`NodeProxyHTTPClient`.

**Synchronous frame delivery causes head-of-line blocking across all multiplexed streams on a session** — `relay/internal/protocol/session.go:60-76, 258-270`
`Session.Run()` decodes every frame for every stream on one connector session and calls `stream.deliver()` inline; `deliver()` does a blocking send into the per-stream `readCh` (128 × 64KB ≈ 8MB). If one consumer stalls (slow downstream client, stalled `io.Copy`), `readCh` fills and `deliver()` blocks the whole session read loop — no frames for any other stream are processed. All of a shop's POS devices multiplex over **one** session per installation (`hub.go:15,27`). **At scale:** one large download (report/PDF) stalls every other device's in-flight request on that shop until the slow stream drains. **Fix:** decouple delivery from the read loop — per-stream delivery goroutine/queue, or a bounded `deliver()` that RSTs the offending stream on back-pressure timeout instead of freezing the session. Raising `readCh` only widens the window. Add a two-stream regression test (stop draining A, assert B still flows).

### Medium

**AI SSE streams hold a global concurrency slot for up to 120s, starving tunnel relay traffic** — `relay/internal/relay/ai.go:115-126`
AI chat, tunnel relay, public invoices, and image search all acquire from the **same** `RelayLimiter` (default 512). An AI SSE turn holds its slot for the full `aiRequestTimeout` (120s) — far longer than a sub-second POS tunnel request. **At scale:** a wave of slow AI turns can crowd out latency-sensitive POS traffic into 429s; cross-feature blast radius. (Per-shop rate limits help but aren't a cross-fleet cap, and continuation turns skip the anti-burst limit while still holding a slot.) **Fix:** give AI chat (and image search) its own bounded `AILimiter` sized to desired OpenRouter concurrency (well under 512), via a new `POINTY_RELAY_MAX_CONCURRENT_AI` flag, so slow AI work can't consume slots needed by fast POS tunnel requests.

**Fleet status does a disk read + JSON unmarshal per installation (`artifactPresent` in loop)** — `relay/internal/relay/update.go:236-254`
`handleFleetStatus` calls `control.AssignedUpdate` per installation → `artifactPresent` → `Store.readMeta` (`os.ReadFile` + `json.Unmarshal`) on every call, re-reading the same handful of `meta.json` files hundreds of times per request (`artifacts.Store` has no in-memory cache). **At scale:** up to 1000 disk reads + unmarshals per `GET /v1/fleet/status` on a slow PaaS volume. Admin-only, infrequent → medium. **Fix:** resolve presence once per distinct version — collect candidate versions from targets+pins, `Get` each into a `map[string]bool`, pass a closure reading the map. Optionally add an RWMutex-guarded `map[version]Meta` cache in the Store.

**`CachedInstallationStore.GetInstallation` bypasses the cache entirely** — `relay/internal/control/cache.go:54-59`
Unlike `validateToken`/`ValidateAIAccessToken` (cache-first, back-fill on miss), plain `GetInstallation` always hits Postgres. Hot callers: token-refresh (`http_server.go:696`), AI tunnel setup (`:2608`). **At scale:** every relay-ticket refresh / install-by-id lookup is an avoidable single-row Postgres query + pool checkout, often microseconds after the same row was cached. **Fix:** make it cache-aware like `validateToken` — read `s.cache.GetInstallation` first, on miss fall through and `cacheInstallation` the result (reuses existing TTL + invalidation). (The access-token AI path is already cache-aware; the clearest win is token-refresh.)

### Low

**No singleflight on installation cache misses (Postgres stampede)** — `relay/internal/control/cache.go:302-309`
On TTL expiry (30s) or a Redis error (treated as a miss via `err != nil || !ok`), concurrent requests for the same installation each query Postgres. No coalescing; same in `ValidateAIAccessToken`. **Downgraded to low:** single PK lookup, cheap; relay control plane, not POS hot path (POS device auth hits local Django). **Fix:** wrap the miss path in `golang.org/x/sync/singleflight` keyed by installation id (already vendored as indirect); distinguish a Redis error from a genuine miss so transient errors don't disable caching.

**Installation search uses leading-wildcard LIKE with no trigram/index support** — `relay/internal/control/postgres_store.go:277-293`
`lower(col) LIKE '%term%'` across three columns + `ORDER BY created_at DESC, id ASC` with no supporting index. Admin-only, bounded to ≤1000 rows → low. **Fix:** add a btree on `(created_at DESC, id ASC)` (the fleet-status listing is the common case); optionally pg_trgm GIN indexes per searched column for substring search. The `(created_at, id)` btree alone is the pragmatic minimum.

**`writeJSON` re-marshals every response payload twice** — `relay/internal/relay/http_server.go:2855-2872`
`jsonSize(value)` does a full `json.Marshal` just for Content-Length, then `Encode` marshals again. 137 call sites, mostly tiny payloads; larger ones (`handleListInstallations`, holiday lists) are low-frequency admin endpoints (AI streaming uses SSE, not this). **Fix:** marshal once into a buffer, set Content-Length from `len(buf)`, `w.Write(buf)`; delete `jsonSize` and the `Encode` call (drops the trailing newline — harmless, makes Content-Length exact).

**Tunnel relay buffers entire request and response bodies into memory** — `relay/internal/relay/http_server.go:2192-2227`
When `MaxRelayedResponseBodyBytes > 0` (default 50MB, active in prod), the whole response is read into a `[]byte` before any byte is written. (The request side already streams via `request.Write`; only the response buffers.) Not the POS hot path — this is remote/cloud access to the on-prem backend. Capped at 50MB/request → low. **Fix:** stream with `io.Copy` through a byte-counting wrapper — but preserve the clean pre-header 502 "too_large" path (buffer up to a small threshold to decide, or trust Content-Length, then stream). Apply to the duplicate at `:959-962`.

**SSE writer marshals JSON and `Fprintf`-formats per token delta with no buffer reuse** — `relay/internal/relay/ai.go:448-458`
Each delta allocates a fresh `map[string]string` + `json.Marshal` + `Fprintf` + `Flush`. I/O-bound (the flush syscall dwarfs the tiny alloc) → low. **Fix (optional):** reuse a per-stream buffer (sync.Pool) and `w.Write` pre-assembled frame bytes instead of `Fprintf`. Do **not** hand-roll JSON string escaping — let `encoding/json` escape.

**`OpenStream` context cancellation is never actually awaited (non-blocking select with default)** — `relay/internal/protocol/session.go:84-95`
The `select` has a `default` branch, so it never blocks on `ctx.Done()` — the plumbed `streamOpenTimeout` is silently a no-op for a stalled/contended `writeMu`. On every proxied request's critical path. **Fix:** remove the misleading select; enforce the timeout on the *serialized* write path. **Do not** call `SetWriteDeadline` directly from `OpenStream` (it mutates the shared conn, racing concurrent writes) — instead add a ctx-aware `WriteFrame` that sets/clears the deadline under `writeMu`, or run `WriteFrame` in a goroutine and select on `ctx.Done()`.

**Frame header + payload written as two unbuffered writes; triple payload copy on the data path** *(merged: `frame.go:82-98` + `session.go:223-263`)*
`WriteFrame` issues two `conn.Write` calls on an unbuffered TLS conn — the 16-byte header becomes its own tiny TLS record per frame (~2× syscalls/records on bulk transfers). Separately, every payload byte is copied 3× (ReadFrame alloc, Stream.Write chunk copy, deliver copy) with no pooling. Relay tunnel path, not POS hot path → low. **Fix:** coalesce header+payload via `net.Buffers{header, payload}.WriteTo(conn)` (one TLS record). Drop the redundant `deliver()` copy — `ReadFrame` already returns an owned, single-use buffer that the read loop never reuses (the safe, zero-risk win). Pool the Stream.Write chunk buffer via `sync.Pool` (safe — written synchronously under `writeMu`); do **not** naively pool ReadFrame's buffer (it escapes into `readCh` with no return-to-pool lifecycle).

## 7. Cross-Cutting Themes

1. **Heavy serializers embedded in list endpoints.** `ProductCatalogSerializer` is embedded by `StockMovementSerializer`, `StockItemSerializer`, and itself carries a prefetch-bypassing `modifier_group_details`. The systemic fix is a **lightweight list/summary serializer** distinct from the full retrieve serializer, plus matched prefetches on every viewset that embeds the heavy one. The frontend often doesn't even read the embedded tree (StockMovement) — audit list serializers against what the client actually parses.

2. **Aggregation in Python over unbounded time-series tables.** Fraud sweep, Z-Report, discount analytics, dashboard purchasing, the AI `customer_insights`/`project_forecast`/`inventory_intelligence` tools, and the notification specs all `list()`/loop rows that GROUP BY/`aggregate()`/HAVING/`Greatest()` should do in the DB. Standardize on SQL aggregation with DB-side `filter`/`order_by`/`[:limit]`, and reserve full-row materialization for genuinely-bounded evidence/detail sets.

3. **Missing composite indexes on status-filtered, time-ordered tables.** `Order` already has `(status, -created_at)`; `PurchaseOrder` and `Job` should mirror it, and `Product` needs a (partial) `name` index for its default ordering. Any model with `ordering = ["-created_at"]` + a `filterset_fields` status is a candidate.

4. **Unbounded / no-cap export & "load everything" endpoints.** The analytics export (entire table in RAM), `outstanding-received-not-paid` (full received-PO history pre-pagination), and the operations job page-drain all bypass pagination by materializing first and trimming after. Pattern: enforce a date window / row cap, stream large outputs (`StreamingHttpResponse`/`zipstream`), and let `paginate_queryset` slice **before** evaluation. The repo already has the primitives (`LEDGER_ROW_LIMIT`, `StreamingHttpResponse`, the cost-history action's correct pattern) — apply them consistently.

5. **Work on the wrong thread / wrong tier.** Notifications recompute belongs on the existing Celery beat (not inline on every GET); AI file base64 belongs on a background isolate like images already are; the relay needs a separate concurrency pool for slow AI streams vs. fast POS tunnel traffic, and per-stream delivery so one slow consumer can't block a shop's whole session.

6. **Shared client infra adopted unevenly.** The codebase has `DebouncedSearchField` (350ms + revision guard) and `PointyDataList`/`InfiniteScroll`, but the contacts screen and both contact pickers use raw `TextField`s, and the operations board page-drains instead of paging. Route **all** search through `DebouncedSearchField` and **all** growing lists through the paged/virtualized infra.

7. **HTTP connection pooling & per-version caching on the relay.** The relay is a fan-out point but uses defaults that defeat reuse: `MaxIdleConnsPerHost=2` to OpenRouter, a bypassed installation cache, no singleflight, and per-installation disk reads for a handful of artifact versions. One tuned shared `*http.Client`, cache-aware `GetInstallation`, and per-distinct-version artifact resolution remove most of it cheaply.

8. **Frontend image caching is in-memory only.** No `cached_network_image` anywhere; every product image is `Image.network`. On a virtualized catalog over a relay tunnel this is recurring re-download churn. One dependency + two widget swaps fixes both call sites.
